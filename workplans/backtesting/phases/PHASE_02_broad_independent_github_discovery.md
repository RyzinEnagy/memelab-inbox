**Role:** Independent software auditor, quant engineer, microstructure researcher and test skeptic. **Complete ONLY phase 02.** Use the project's existing language/architecture unless the audit proves a change essential.

Read current project records, `START_HERE.md`, `EXECUTION_RULES.md`, appropriate `references/*.md`, the previous phase evidence and the current repository HEAD.

## Single verifiable objective

Broad independent GitHub discovery. Produce a narrow, inspectable outcome that directly enables the next phase. The complete module is **not** automatically claimed finished by this phase.

## Required execution

- Execute `RESEARCH_PROTOCOL.md` across official GitHub search/code/topics, project docs, release/PR/issue history, ecosystem link traversals, curated lists, and non-GitHub package indices. Use at least six query families and >=40 **unique** relevant public repos; seed URLs aren't quota fulfillment if stale/dead.
- Include mainstream vectorized and event-driven engines, crypto strategy packages, Solana/AMM-specific math, event/catalyst data, factor/validation, portfolio, slippage/latency and timeseries storage/replay. Look beyond 'memecoin' in repository descriptions.
- Capture search exact query, engine/API, date, number found, inclusion/exclusion, repo URL and commit. De-duplicate renamed projects/forks while keeping genuinely distinct maintained successors.
- Build a first-pass landscape matrix; independently follow promising author links, dependency graphs, comparative writeups and references to identify missing competitors. Challenge popularity bias by locating at least five credible low-star niche candidates.
- Partition longlist into at least 20 that merit source-code inspection, plus transparent rejects, and note research gaps due to rate limits/authentication.

Prove a test or source-code finding **catches** it. Check upstream and downstream assumptions; attach the counterexample and commands. If a source is unavailable, explicitly record what remains unverified and whether later phases may proceed using *test-only* artifacts with that limitation.

Apply `EXECUTION_RULES.md` bounded loop: **inspect → implement/research → run positive/negative/regression tests → adversarial review → repair → rerun → gate**, maximum five full passes. Keep per-pass test outputs, counts, exit codes, time, SHA and exact changes. Do not call PASS with a skipped key test or mutate acceptance criteria to get green. If blocked or still red after pass five, mark FAILED/BLOCKED/NEEDS_REVIEW with next action.
