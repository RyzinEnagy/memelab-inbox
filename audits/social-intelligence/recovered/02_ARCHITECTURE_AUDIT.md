## 2. Executive assessment

**Strengths worth preserving:** numbered social migrations with checksums, transactional application and explicit backups (`schema.py:1290–1355`); source observations, provenance and evidence-link entities; distinct chain+contract token identity (`schema.py`, `store.normalize_contract`); separation of private exact text from published metadata (`private.py`, `store.py`); append-oriented narrative, chronology, performance and outcome run records; careful refusal to equate a wallet assertion with confirmed control; repeated deterministic test fixtures. The project has substantive, functioning offline components; a wholesale rewrite is unjustified.

**Most serious architectural deficit:** event-time and knowledge-time are not enforced by a common read contract. An immutable record is not a reproducible *historical* conclusion unless the engine also knows *when that record and its dependencies became available*. Phase 01 proved future-extracted claims (AUD-001), backdated replay inputs/current wallet linkage (AUD-002), an explicit future narrative run accepted by an earlier feed (AUD-015), and future-created chronology flags selected for old feeds (AUD-017). The consequence is research look-ahead bias and inability to reliably reconstruct the belief state at a past decision time. This affects reproducibility more than ordinary component correctness.

**Release gate:** Do not certify historical trader efficacy, trader rankings, backtests or automated signals until the temporal invariants, live ingestion→extraction handoff, and durable social state across restarts are verified end to end.

### Readability, coupling, typing, configuration and dependency review

- **Coupling:** `feed_store` combines narrative, trader registry, market-context, current chronology and JSON decoding; `chrono_store` consults social/wallet and price series. Central orchestration is justified, but read dependencies must receive explicit cutoff+version context rather than global 'latest'. API/CLI modules are often distinct, which is positive.
- **Duplicate abstractions:** Parallel wallet attribution/assertion/registry links encode substantively different stages; *do not* collapse them without a data dictionary and preservation mapping. Two or more SQLite state stores also serve confidentiality/delivery boundaries rather than pure duplication.
- **Exceptions and logs:** ingestion provides `log_event` with redaction and unit-level health; iterator exceptions sit outside the unit guard, while feed chronology error is broadly swallowed. Instrument causal trace IDs across collector → observation → extraction → narrative → report → alert/outcome, logging failure status without exact private text.
- **Type and validation:** good CHECK constraints and parser safeguards exist, but SQLite REAL timestamps permit mixing event, ingestion, extraction and derived-run clocks unless semantic contracts enforce them. Python annotations and a `SourceAdapter(Protocol)` help but are not runtime safety guarantees. Enforce finite timestamp ranges, canonical chain IDs, normalized address shape, positive budgets and typed run status at boundaries.
- **Performance:** no Phase 02 EXPLAIN plans, production load benchmarks, stress races or query-profile samples were run. Potential hot loops include feed per-market-field latest-fact queries (`feed_store._market`) and many per-entity registry/history lookups. Benchmark with realistic cardinalities and `EXPLAIN QUERY PLAN` before modifying indexes. This review finds **risk**, not verified slowness.
- **Circular dependencies:** no import-cycle execution probe was run; **not established**. Where imports are deferred (`feed_store` → `chrono_store`/`narratives`), they should be captured in a dependency test rather than treated as conclusive evidence of a cycle.
- **External dependencies:** no newly unnecessary mandatory dependency was proven. Separate optional provider SDKs/configuration and paid model transports behind explicit disabled-by-default adapters; avoid replacing known working code or choosing new database frameworks without demonstrated need.
- **Configuration:** environment-dependent DB/private-store paths and `.example.json` files are reasonable; define a single validated run config snapshot with version, public-safe redaction, retention, time zone, provider scopes, billing and fail-closed defaults so emitted research identifies the configuration that created it.

## 4. Data lineage and historical reconstruction contract

**Can the current system reconstruct precisely why a given published conclusion was generated?** **Not reliably across time or restart.** Some individual derived runs store complete input/result JSON and hashes; some source claims retain observation provenance; append-only records are an excellent basis. But historical selection can import future extractions/chronology, current wallet links can contaminate replay, the primary ingestion handoff is absent, and social/private/outcome stores are not consistently included in the existing continuity export. A hash proves that bytes match a stored input, not that input was **knowable then**, complete, licensed or selected consistently.

Proposed minimal proof chain:

`publication_id → code commit + parameters + scoring version + publication_time + event_cutoff + knowledge_cutoff → narrative_run_id + extraction_ids + market_fact_ids + wallet_assertion_version_ids + chrono_run_ids → observation_ids → source provenance/provider ID + source published time + first available/observed time + content hash + access mode + coverage gaps`

Every arrow must be persisted, every eligibility timestamp must be tested, and publication correction must produce **a new immutable version** that points back to the original with a reason. Distinguish:

1. **Observation:** what source/platform or chain actually returned; ID/hash, event timestamp, collected/available timestamp, provider/source scope, retrieval health and method.
2. **Inference:** token interpretation, actor relationship, possible common-control cluster, narrative stance, price-risk signal; with confidence, evidence refs, algorithm parameters and reviewed state.
3. **Publication:** frozen conclusion, explicitly uncertain if completeness insufficient, its inputs and revision history, with reproducible `as_known_at` eligibility.

### Identity and provenance specifics

- **Token keys:** use normalized `(chain, contract/mint)` for social layer and chain-qualified map when projecting to legacy `mint`; never merge by ticker or name. EVM hex casing/chain_id and Solana base58 case/length need separate validation. A raw address string and a validated contract identity are not equivalent.
- **Wallet attribution:** an unreviewed self-claim or common-funding hypothesis cannot silently become proof of control. Corrections/retractions are newly timestamped assertions, not retroactive rewriting; preserve prior scored versions and explain changed conclusions.
- **Source availability:** `published_at` can precede the first time collector could see it. Use observed/ingested/processed/known times separately; provider backfills must not create fictional earlier knowledge.
- **Deduplication:** item identity, observation identity, content versions, repost dependence and downstream claim hash are different keys. Preserve repost events while discounting their purported independent evidence, and make reprocessing idempotent with a versioned operation key.
- **Timestamps:** use UTC seconds for persistence, capture clock origin and null basis, and convert to local display only at UI/report layer. Existing old schema TEXT timestamps require typed adapters, not implicit textual comparison.

## 5. Compatibility and migration strategy

The Phase 01 copy test migrated a legacy database to social schema version 12 without changing counts in its 20 legacy tables, and reopen/rollback tests passed. This **supports structural coexistence**, not proof of safe unattended upgrades or cross-store restore. Social schema deliberately avoids foreign keys into legacy tables. The existing watchlists, theses, entries, and history are built around legacy `mint` identifiers, while social sources use chain-qualified identity; do not attach social conclusions by mint-only string when chain is ambiguous. The `state.py` JSON exporter restores legacy watchlists/theses but does not preserve social intelligence or private material. Existing social reports and alert/outcome ledgers may live in distinct SQLite files; a public state snapshot is not a consistent full-system backup.

Upgrade plan (without implementing now): take an SQLite online backup, run `PRAGMA integrity_check` and `foreign_key_check` on a copy, validate baseline table counts/checksums, apply checksummed forward migration on a clone, restore and rerun representative historical outputs, verify no private data enters committed public state, then rehearse rollback by restore-from-backup rather than destructive migration downs. Schedule no migrations concurrently with collectors/writers. SQLite WAL helps concurrent readers but not multi-DB atomicity.

Incremental SQLite hardening with shared temporal/evidence contract, outbox, and restore tests** | Keeps proven source adapters, current schema and legacy memelab integration; adds explicit invariants with limited changes | Requires careful contracts across multiple readers/writers | **Recommended** |

## 7. Prioritized remediation acceptance gates (for later phases, **not executed here**)

1. **Temporal integrity:** prove a future extraction/chronology/wallet link/publication cannot appear in historical `as_known_at` queries, including explicit ID and supersession cases (AUD-001,002,015,017).
2. **Integrity / restart:** every DB connection has active foreign keys; a seeded multi-chain collision cannot join wrong token; orphan scan clean; public/private/signal state restores coherently without exposing private records (ARCH-002,005,006,011).
3. **Pipeline:** one genuine (authorized) source item flows through normalized ingest, private text, resolved claim, narrative, cited report, opt-in alert and later outcome with dedupe on replay; unsupported sources remain blocked (AUD-003,007,014).
4. **Failure safety:** loss between pages, iterator error, crash before acknowledgement, simultaneous workers and repeated migrations produce terminal health, safe resume, no gaps and no silent double scoring; source cursor does not skip data (AUD-005,016).
5. **Evidence/accountability:** every report carries manifest and can reproduce the original conclusion and a later corrected publication independently, even after attribution revisions.
6. **Capacity and policy:** measure table growth and query plans under realistic volume; enforce billing limits and source-specific deletion policy without destroying permitted non-content lineage.
