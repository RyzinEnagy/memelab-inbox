## Findings

All MINOR. None changes a number, a verdict or the phase status.

- m1 (coverage label, later phases). 12 of the 15 "CENSORED_RETRIEVAL / OUTSIDE_FETCHED_WINDOW" decisions are pools younger than 24 h at T: the export's `first_pool_at` equals the first fetched candle within 0.1 h (ages 0.5 h to 18.5 h), and each fetch asked for T - 25.1 h with status OK in one or two calls. That history did not exist; it is not a retrieval gap. The other 3 are older pools (43 h, 43 h, 66 h) with no candles before 15 to 19 h. The label follows the frozen version 2 rule (RETRIEVAL basis), so no number moves, but the model card describes the technical population as "PIT route with 24 h of fetched history" without saying it excludes every pool under 24 h old. For Phase 17 this means tech-1 models can never score the youngest pools, the bulk of live memecoin candidates. Suggested: state it in the card, PI-D-051 and HANDOFF.
- m2 (tests). 12 of my 18 mutations of `technical.py` pass all 40 phase tests: a value's availability taken as the earliest input instead of the latest (blinds the P36 guard and the "0 inputs after T" evidence), score-time re-standardisation (CX-S08), a fetch series ending 1 h before T accepted as covering T, the P13 guard weakened by one day, the identity join ignoring decision time, the failed-breakout and retest comparisons at equality, the stump minimum leaf off by one, `SPLIT_EPS` set to 0, the version 2 derived tolerance loosened to 1e-3, NC1 using one seed for every seed, and the fit's own maturity check removed (the last is redundant with `check_asof`). The first three are caught only by run outputs (trap flags or the second trace), not by tests. "28 of 28 mutations caught" is true for the phase's own list only.
- m3 (silent runtime). `run_technical.py` exits 0 when a trap fails: under the availability and boundary mutations it wrote `NC2T.pass: false` (5 and 9 future values accepted) and still exited 0. `write_results.py` would carry `pass: false` into RESULTS, so the records would show it, but the runner itself does not stop.
- m4 (timestamp). The ledger and `DEBUG_RUNS` say the features-only probe ran "about 21:40Z", before the code commit. That text was committed at 21:22:26Z, so the time is impossible; the tool log and the scratch file put the run at about 21:16Z (after the pre-registration, before the code commit, so the substance holds).
- m5 (description). The run-1 P06-T defect is described as the last close's age. The value the probe actually counted was `tech_log_ret_1h` of `55257a0b...` (12 values of that decision changed, all clock-only). The pre-registered wording ("the values that would change ... are refused") was reinterpreted after the result; correctly, and disclosed, but the reinterpretation should be named as such.
- m6 (oracle scope). The lbfgs check compares solvers on the lab's own preprocessed design (`_Z` from the npz), so it never tests `stats.Prep`; the holdout-start cards (144 rows) are not cross-checked. PI-D-051 item 5 switches later oracles to Newton solvers; fine as a forward rule, but G16 should stay "failed as registered, explained", not be re-scored as a pass in the repair pass.
- m7 (fragility). Both fitted T1b states sit exactly on the minimum: fold 4 138 rows with 20 positive, holdout card 144 with 20. One positive changed by the Phase 06 48 h re-read turns every fitted Phase 08 model into INSUFFICIENT_HISTORY. Worth naming in the PROVISIONAL note so the rerun is not skipped.
- m8 (wording). PI-D-051 item 1 says "no technical model is distinguishable from the base rate", which reads like the verdict NOT_DISTINGUISHABLE_FROM_BASE_RATE (a tested negative). The verdicts are INSUFFICIENT_HISTORY and INSUFFICIENT_DAYS (not testable). The model card's wording ("cannot be called better or worse") is the right one.

## Counterexample CX-S08: score-time re-standardisation

Wrong but plausible: a later change "fixes" a scale mismatch by keeping the card's columns, medians and indicators but standardising the rows being scored with their own mean and sd (the common `scaler.fit_transform(X_test)` bug). Each forecast then depends on the other decisions of the same day, some of them decided after it (look-ahead across rows), and train-only standardisation is broken. Script: `skeptic/p08_counterexample.py` (out: `p08_counterexample_out.json`). Result: all 40 phase tests pass, the runner exits 0, the phase mutation probe has no such mutation; the T1b M2 Brier goes from 0.0040 to 0.0436 and its BSS against B0 from +0.729 to -1.952 (M1 +0.690 to -1.295), and the verdict stays INSUFFICIENT_DAYS. What catches it: only `verify_trace.py` on the second trace (`M2: independent 0.12040 vs trace 0.29836`), the trace added after recorded run 1, and comparison with the committed outputs or with my independent recomputation. The pre-registered trace (no fitted model) does not catch it. Suggested test: score a fitted card on one row and on that row inside a batch with others; the number must be the same.
