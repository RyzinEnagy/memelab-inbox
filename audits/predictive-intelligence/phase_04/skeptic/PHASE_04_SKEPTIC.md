## Findings

### MATERIAL

**M1. The lock guard accepts lines that make the lab's install route run `setup.py` or install a file whose sha256 is not locked (P32; B15 fail condition met).** `runtime._REQ` allows an environment-marker group `(\s*;\s*[^\\#]+?)?` that swallows everything after `;`. With a marker present, `check_lock` returns `[]` for `p04sk==1.0 ; python_version >= "3" --hash=sha256:<sdist hash> --only-binary=:none:`. pip parses that per-line `--only-binary=:none:` into the finder's FormatControl and clears the command line's `--only-binary=:all:`. Run with exactly `R.INSTALL_FLAGS` plus a local index, offline, pip 26.2.2: the plain line is refused (as in the phase's demo), the marker line builds the sdist and `setup.py` writes its marker (`lock_bypass.json`, verdict BYPASS). Same root cause: `pkg==1.0 ; python_version >= "3" --hash=sha256:<legit> --hash=sha512:<other wheel>` passes `check_lock`, and pip installs the other wheel, because pip accepts a file that matches any listed hash (`installed_value: evil`). Nothing in the repository catches either: `check_lock` returns `[]`, all 46 runtime tests pass, `hostile_setup_demo.py` only tries a line without a marker, and the test that reads `research-py313.txt` checks format, not that its hashes are PyPI digests. PI-D-032 ("the flags refuse any sdist (no setup.py or build backend runs)") and BOM_LOCKS.md state the opposite. Fix: after the requirement and optional marker, allow only `--hash=sha256:<64 hex>` tokens; refuse any other token that starts with `-` anywhere in an entry (`--only-binary`, `--hash=sha384/512`, `--config-settings`, `--global-option`); forbid `--` inside the marker group; add both lines as negative cases in `test_p32_lock_guard_refuses_anything_but_hashed_exact_pins`; optionally pin the sha256 of the lock files in a test so any edit needs a recorded decision.

**M2. `runtime.py` "never raises" is false on concrete inputs (B13 fail condition "a crash where a state is expected" met; PI-D-033 misleads Phase 17).** From `runtime_probes.json`:
- `guarded(name, fn)` lets `SystemExit` through (`except Exception` does not cover it). Any optional component or CLI `main()` that calls `sys.exit` ends the caller; MiroFish alone has 10 `sys.exit` calls in its backend and scripts, including the missing-key path (`backend/run.py:28-33`). `simulation_state` and `capability_report` ("Never raises") propagate it too.
- `simulation_state` / `capability_report` raise `ValueError` for `llm_actions` = "many" or NaN, `OverflowError` for inf, `TypeError` for a list or dict, because `int(run.get("llm_actions") or 0)` runs outside `guarded`. `llm_actions` = True or "5" count as AVAILABLE.
- `capability_report` raises `AttributeError` for a config whose `predictive` or `behavioral` section is not an object (`{"predictive": true}`, `{"predictive": "on"}`, `{"predictive": {"behavioral": "yes"}}`, a top-level list). `contract.enabled` (Phase 01 code, the flag Phase 17 reads) raises the same for `{"predictive": true}`, `[]` or `"x"` in `data/config.json` instead of returning OFF.
- The suite does not pin the broad catch: narrowing `except Exception` to `(ValueError, RuntimeError, MemoryError)` leaves all 46 tests green (`mutations.json`), so a `KeyError`, `TypeError` or `AttributeError` from a component could escape after a later edit without any test failing.
Fix: catch `BaseException` minus `KeyboardInterrupt` and `GeneratorExit` in `guarded`; accept `llm_actions` only as a non-bool int >= 1 and treat anything else as NO_LLM_ACTIONS; type-check every config section (non-dict means OFF / NOT_APPROVED); add tests for each probe above, including `SystemExit` and a `TypeError` from a component.

### MINOR

**m1. The fold audit (prototype `core_numpy.fold_audit`, to be ported in Phase 07) is fail-open and trusts its inputs.** On the real 24 h sample with the maturity purge removed (29 labels mature after their test start, 31 after their cutoff, both reproduced): one test row per fold with a NaN decision time gives `valid_walk_forward: True` and counts 0 leaks; NaN maturity on the 31 leaking training rows gives True; a declared cutoff two days after the test start gives True (a model card would claim training after the decisions it predicts, P13); a 6 h maturity column supplied for 24 h labels gives True on the supplied column while 31 labels mature after the cutoff on the true one. Same mint in training and test: 1, 4, 4 and 1 of the 7, 8, 7 and 4 OOS rows (allowed by the frozen plan as a sensitivity, but the audit has no group field). `validate_rows` would refuse non-finite times if run first. When porting: refuse non-finite times, require cutoff <= test start, recompute maturity from decision time and the target's horizon, report shared mints.

**m2. The runtime tests are weaker than "17 of 17" suggests.** Of 10 further mutations, 6 survive with all 46 tests green: shingle hash changed from sha256 to sha1 (MiroFish files flagged by the gate drop from 81 to 0, so P31 becomes a no-op), lines lower-cased before hashing (81 to 65), breaker counting only network failures (an HTTP 500 raised as RuntimeError never opens it), call and cost caps mapped to no abstain reason, banned options checked only at line start, and the narrowed catch of M2. Cause for P31: no test compares the fixture's recorded `hash`, `normalization`, `shingle_lines` and `winnow_window` with the runtime constants, and the suite has no positive control against the pinned sources (which cannot be committed). Suggested: assert the fixture parameters equal the runtime's; store a few fingerprints of a synthetic text made by the same builder and assert the runtime reproduces them; a skip-if-absent test against the pinned clone.

**m3. Copyleft scan scope.** The in-suite P31 test scans `memelab`, `tests`, `tools`, `bridge`, `skills`; 193 tracked code files under `audits/` (including the MiroFish adapter prototype) and three root scripts (`bootstrap.sh`, `commit_file.py`, `tools_bundle.py`) are outside it. The phase's one-off build scan covered the prototypes and I found 0 fingerprint hits in all 402 tracked code files today, so nothing is copied now; a later copy into `audits/` or a root script would not fail the suite. `.json`, `.md`, `.ipynb` and `.css` are not scanned; copies under 15 normalized lines pass (stated by the phase).

**m4. The GeckoTerminal boundary behaviour is wider than "inclusive".** For an unaligned `before_timestamp`, 55 of 83 bodies end with the candle that starts at `floor(before/300)*300`, i.e. the candle containing the boundary, which covers up to 300 s after it (26 of 30 aligned requests end with the candle starting exactly at the boundary). PI-D-034's rule "drop candles at or after its own boundary" is safe for a 5-minute-aligned boundary such as H0, so Phase 04 is unaffected. A later backfill with an unaligned boundary (a decision time, a maturity time, a prospective as-of) must drop candles whose end is after the boundary (`start + 300 > boundary`), not only those starting at or after it.

**m5. BAKEOFF_ONLY isolation is documentary.** No code refuses `adoption/data/dev_t1_*.csv` or rows with `use=BAKEOFF_ONLY`; PI-D-034 and a docstring are the guard. The raw store `/home/claude/pi_research/p04_gt_raw` still holds the 6 candles that start at H0 (first 5 minutes of the retrospective holdout). No holdout label, eligibility or prevalence was computed in this phase (checks 7 to 10). Phase 06 should not read that store for holdout work, or should drop those candles first.

**m6. CallGuard and dependency probe edges.** A NaN `cost_per_call` or `max_cost` disables the cost cap (5 of 5 calls allowed with a cap of 1); a callable that returns an HTTP 429 or 500 status instead of raising never counts toward the breaker (callers must raise; say so in the docstring). `dependency_state("pkg.sub")` imports `pkg` (marker written), contrary to "without importing it"; refuse dotted names or probe only the top-level name.

**m7. Equivalence claims hold on regular inputs only.** numpy Platt on constant scores stops at its starting point (b 0.4700 against scikit-learn's 0.4866, probability difference 0.0039); the error table already calls this case silent, but the "within 5.9e-8" sentence has no such qualifier. The Venn-Abers oracle probes pass raw scores through a sigmoid: with scores above about 37 the oracle sees ties the numpy code does not and the outputs differ by 0.15 (numpy is the correct side). Phase 13's oracle tests should feed probabilities to both.

**m8. Cosmetic.** Rollback leaves an empty `mpl_toolkits/` directory (the manifest counts files only, so `rollback_clean: true`). `core-py313.txt` carries the research lock's header ("research dependencies ... never into the interpreter that runs the scheduled lab") although it pins the lab's own numpy. The bake-off lowers the first-fold minimum from 100 to 30 on the real samples; this is disclosed in BAKEOFF.md as a bake-off setting and is not a change to ACCEPTANCE.

## Counterexample (new): a lock line that passes the guard and runs a hostile `setup.py`

Script: `/home/claude/pi_orchestration/skeptic/p04/skeptic_04_lock_bypass.py`, output `lock_bypass.json`. A dependency update adds one line to `research-py313.txt`: `p04sk==1.0 ; python_version >= "3" --hash=sha256:<sha256 of the sdist> --only-binary=:none:`. It looks like an ordinary universal-lock line with a marker and a hash; the only unusual part is the short option tail. `runtime.check_lock` returns no problem, so the P32 test that reads the lock would stay green. Installing with the documented route (`--require-hashes --only-binary=:all: --no-deps`, offline, local index) builds the sdist and its `setup.py` writes the marker file; the same package on a line without the marker is refused. A variant with an extra `--hash=sha512:` installs a wheel whose sha256 is not the locked one. What catches it today: nothing in the repository (`check_lock`, the 46 runtime tests, `hostile_setup_demo.py` and the lock-format test all pass). What would catch it: the stricter token rule of M1 plus a test with these two lines.
