## Frozen rules of report-1 and alerts-rules-1 (fixed here, before any code)

1. Reading. Reports and alerts read the predictive state only through `integration.load_state` (each line's record id, the pass chain and each file's sha256 as recorded by the last pass) and `integration.check_state` (each document owned by an attempted request of its pass that lists its forecast id, each attempted request owning exactly its documents, unique forecast ids, each document paired with its record). A document is used only with its record (`integration.pair_errors` empty) and its owning request; the backtest veto, decision support, staleness, catalyst state, served registry state and the raw number are read from that request record (Phase 17 note: a FORECAST document's backtest veto lives in its request record). A FORECAST is shown with numbers only when, in addition: its record lists no condition; the request's target entry says FORECAST, holds a finite raw number and the calibration card sha the document cites; the stored calibrated point and interval equal the document's (tolerance 1e-12); the model card and the calibration card resolve from the registry the request names (`integration.load_registry`, `_load_card` with the card file sha256 and model sha checked, `_calibration_card` with the card sha checked); and `integration.check_document` with both cards and the flag read from the config returns no error. Otherwise the target is shown as DOCUMENT_REFUSED with the failed checks and no number. A state that fails `load_state` is STATE_TAMPERED; a state with `check_state` problems is STATE_CHECK_FAILED and every document named by a problem is refused; neither ever shows a number.
2. Lab snapshot (optional, read-only). With a lab database (`integration.connect_lab_ro`, `mode=ro`, `query_only`), the report reads the thesis rows of the mint and keeps the one whose `integration.snapshot_sha` equals the request's snapshot hash (SNAPSHOT_VERIFIED) and its token row. Without a database, or without a matching row, the report says SNAPSHOT_NOT_VERIFIED and shows no fact from the lab row (age, symbol, lifecycle, structure are UNKNOWN). Facts are never taken from a row of another snapshot.
3. Flag. `contract.enabled` false: the report and alert commands print FLAG_OFF, read nothing but the config and write nothing. No lab module imports `reports.py`; the lab's outputs with the flag off are byte-identical (the Phase 17 real-path comparison is repeated at the Phase 18 frozen commit against `b0fad12`).
4. No unsupported number (P24, P38, P27). An ABSTAIN target shows "no probability", its named reasons, the record's plain explanations and what would unblock each reason (the frozen UNBLOCK table, one line per contract reason). For an abstaining target no base rate, cohort number, reference-model number (B0, B2), calibration-set fraction, Brier or skill number, or score-like number is shown. Counts of events are allowed (they are not probabilities). A verified FORECAST shows point and interval as whole percents, the calibration level, base rate (the card's training prevalence), cohort, support n and k, model id and sha, training cutoff, calibration card sha, its caveats, and the line "price path only: not proceeds at any size (PRICE_PATH_NOT_PROCEEDS)". No text says a forecast changes, raises or boosts the 100-point score, a status, the watchlist or a list.
5. Required fields per target (prompt item 1): exact `chain:mint`; token age at the snapshot (the vendor's first pool time from the verified token row, HEURISTIC) or UNKNOWN; snapshot hash, row sha256, decision time and its basis, capture time, inputs observed time and age at capture, INPUT_STALE when older than 7,200 s; target id, version, plain words and horizon; status and reasons; probability and interval or none; cohort N and base rate or "not shown: no model selected"; data snapshot sha, feature set sha and model sha; training cutoff; risk flags (lab fatal flags, veto unknown, backtest veto); stale warnings; limitations (the document's caveats, the not-attempted registry targets with their registry status and reason).
6. Sections in fixed order (prompt item 2), each line in the lab's buckets rendered by `memelab.report._ev`: report header and FORMAT-ONLY watermark when any fixture document is present; at a glance (opportunities by target status, probabilities shown n of m, vetoes, backtest, simulation); system status (flag, integration version, registry state and each target's mode and pin reasons, Phase 13 calibration status, BACKTEST_NOT_AVAILABLE and what unblocks it, SIMULATION_NOT_AVAILABLE and why, depth collector, state check, frozen cards MODEL_STALE after 2026-10-31T00:00:00Z); target definitions (from `contract.TARGETS`: barriers, horizon, positive and negative outcomes, tie rule, price source, route, caveats; and the non-primary targets with their status and why); carried constraints (Phase 13 rules and the Phase 17 sanitization, rendered as text); then per opportunity: (a) identity and snapshot, (b) the lab's structural research (score, fatal flags, status unless it carries trade wording), (c) technical and chart thesis (the lab's lifecycle and structure labels from the verified row; no zone, level, invalidation or thesis text), (d) catalyst evidence (the exact-address catalyst state the request recorded; ticker and name links are context, not identity, P17), (e) predictive research per target, (f) historical prediction and its out-of-sample record (from the committed `phase_16/registry/REGISTRY_INDEX.json` and the pinned reference entries: mode, reasons, retrospective verdict code and event counts, prospective NOT_YET_MATURED; cross-checked against the request's pin event id, else REGISTRY_INDEX_MISMATCH), (g) execution and stress (structural veto, backtest veto from the request, size basis, depth state, BACKTEST_NOT_AVAILABLE, "no position size comes from a forecast", PRICE_PATH_NOT_PROCEEDS: predicted upside is never realizable exit, P08, P25, P44), (h) behavioral scenarios (SIMULATION_NOT_AVAILABLE: MIROFISH_NO_GO, module off, no approved spend; a scenario in a document is listed by label only as a synthetic hypothesis with no number, P27), (i) sources and ids (forecast ids, record ids, request record id, pass id, registry log sha, calibration card shas, token report file name), (j) limitations. Then the events that were not attempted (UNCHANGED, DUPLICATE, SUPERSEDED_IN_PASS, DEFERRED_*, NO_DECISION_SNAPSHOT, NOT_EXACT_IDENTITY, ERROR) as a visible table, never dropped. Then units and times.
7. Sanitization (Phase 17 m3, m8). Every token-sourced string (symbol, chain, lifecycle, structure, status, token report file name, error labels) passes `integration._ident`; mints only through `integration._mint_text` (exact address or "not-an-exact-address"); no local path is printed (file names only); the lab status is shown only when it carries no trade word (the lab's own words include NEAR ENTRY and ENTRY CONDITIONS MET), else "kept in the lab's token report". The whole report and every alert text pass the trading-word check (`abstention.TRADING_WORDS` through `integration._plain_ok`) plus the Phase 18 list ("target price", "price target", "take profit", "stop loss", "stop-loss", "position size", "all in", "load up", "ape in", "accumulate", "profit") after the exact mints are removed; a failure raises and nothing is written.
8. Format-only fixtures. A report with any document whose `is_fixture` is true carries "FORMAT-ONLY FIXTURE: invented data, not a forecast" as its first and last line and on every FORECAST row; an alert on fixture data carries the same banner first and last. `render` refuses a view with a fixture document and no watermark.
9. Alerts reuse the social-intel conventions. State through `alerts_engine.connect` at a private path (default `data/private/predictive_alerts/alerts.sqlite`, schema `memelab.social.alerts.state/1`; refused inside the repository unless under `data/private/`, refused for the lab database); dedupe key unique per mode; cooldown per policy and key through `alerts_engine._in_cooldown`; a daily cap per local day (America/New_York) counted over the stored alerts; quiet hours through `alerts_core.in_quiet_hours`; local and UTC times through `alerts_core.local_text`; the disclaimer `alerts_core.DISCLAIMER`; previews written through `alerts_transport.FileSink` (preview folder only); delivery ledger rows `dry_run_preview`; runs recorded in `alert_runs`; `alerts_engine.state_view`, `render_state` and `render_run` for the readable state. Mode dry run only: `--send` is refused (no external delivery is approved, PI-D-005) and no transport other than the file sink is ever built.
10. Alert policies (frozen; candidates sorted warning first so the cap never drops a warning for a notice):
    - risk_override, warning, cooldown 6 h: an attempted request whose structural veto is true (any lab fatal flag) or unknown, whose backtest veto is true, whose changes include a liquidity fall of 20% or more since the previous attempt of the mint, or a fatal-flag change that adds a flag. Names every flag; says no forecast clears it; when the request has a FORECAST it says that forecast is overridden.
    - reevaluate, notice (warning for the drawdown target T2), cooldown 12 h: a FORECAST verified under rule 1, level SHADOW or VALIDATED_EXPERIMENTAL, whose interval lower bound is above its base rate. Text: it may prompt re-evaluation only. Suppressed VETO_OVERRIDES_FORECAST when the request carries any veto or unknown veto.
    - forecast_withdrawn, notice, cooldown 12 h: a target with a verified FORECAST in the previous attempt of the mint abstains in the newest attempt; names the new reasons.
    - pipeline_health, warning for STATE_TAMPERED and STATE_CHECK_FAILED, notice for REGISTRY_UNAVAILABLE, ERROR events, and MODEL_STALE or DRIFT_ALERT among a target's blocking states; cooldown 24 h per state.
    - Never an alert for an abstention alone. Suppressed with a reason code: NOT_EXACT_IDENTITY, SOURCE_STALE (inputs INPUT_STALE, or the request's capture more than 24 h before the run), FIXTURE_IN_LIVE_RUN (fixture documents in a run not marked fixture), cooldown, daily_cap, VETO_OVERRIDES_FORECAST. Defaults: daily cap 8, quiet hours 22:00 to 07:00, interval 60 min, dedupe retention 30 days.

## Counterexample CX-18 (pre-registered)

Wrong but plausible: a report renderer that prints `document.probability` whenever `prediction_status` is FORECAST, and an alert engine that evaluates each policy on its own. A document whose probability was edited after `verify_point` ran (with every record id and file sha re-sealed so `load_state` still passes, but the request record left with the true calibrated point), or a fixture forecast placed in a live state, would print a number nobody verified; and a strong forecast on a token whose exit is impossible (CANNOT_EXIT_5K) would send an optimistic re-evaluation notice beside, or ahead of, the warning. Caught by rule 1 (the stored point, the record, the request and the cards must agree, else DOCUMENT_REFUSED with no number), rule 8 (a fixture document makes the whole report watermarked; in a live alert run it is FIXTURE_IN_LIVE_RUN) and rule 10 (VETO_OVERRIDES_FORECAST; warnings sorted first). Tests: the re-sealed forged state renders DOCUMENT_REFUSED and no percent; the impossible-exit fixture gives one risk_override alert and a suppressed reevaluate; removing either check makes a test fail (mutation probe).
