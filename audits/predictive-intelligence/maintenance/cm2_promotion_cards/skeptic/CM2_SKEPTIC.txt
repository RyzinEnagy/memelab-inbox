## Daily cycle

Predictions are appended and committed before any read, and the run stops (PREDICTION_COMMIT_FAILED) if HEAD does not hold the working ledger; `--no-commit` refuses a planned read before any call. Named exit codes, broad exceptions mapped to UNEXPECTED_ERROR, writes outside allowed paths stop it. The lock refuses a concurrent run; a second sequential run is allowed and is idempotent (no ledger line, no call) but adds a run-record commit. Calls: 5.7 a minute, default 60, reader deadline 25 minutes. No new exports: NO_NEW_EXPORTS note and exit 0 (fresh-clone evidence at a8c96d7). The script never pushes.

## Findings (all MINOR)

1. Commit-time anchor is keyed by line number, not content (counterexample below). `commit_times()` gives each ledger line the time of the first commit where the file had that many lines, and no code compares a committed ledger with the previous commit's ledger. Fix before the first window can close: in commit_times, require each commit's ledger to be `is_append_only` of the previous one, or fail the window as NOT_ADMISSIBLE.
2. PROCEDURE.md calls GitHub's push record "the independent time anchor", but the push happens after the run, after the label reads, so it cannot show that predictions preceded reads; it only bounds the run. The script does not check that it runs on feature/predictive-intelligence; "push the branch it ran on" is a scheduled-task instruction, not code. A push (or a second commit-and-push) between the prediction commit and the reads would make the claim true.
3. SHADOW is reachable only as a computed level in the summary: make_entry refuses publishable levels and there is no event that raises a registered level, so a CHAMPION pin can never be written. And the only kind that can pass is B2, a REFERENCE_BASELINE, which `level()` would report as SHADOW while the pins say references are never published. Fail closed, but the records say SHADOW is now reachable; a later change control is needed to make it reachable for a publishable card.
4. `window_results()` filters by target and kind, not recipe_id: a future recipe would inherit the windows count and any passed window of R-CM2-1 (latent; a new recipe needs a pin change).
5. evaluate_window's own negative-class minimum is untested (mutation (a) survives); harmless today because next_window enforces it, but PI-D-126 claims evaluate's own minimums are tested.
6. CLI accepts `--max-calls` up to 300 (the change control says at most 60 per run; the 25 minute reader deadline caps it near 142, within ACCEPTANCE's 1,200), and `--now` is unrestricted outside tests (a future `--now` writes a future registry as_of that blocks later registrations: fail closed). The registered_at of a retrained version is the run start, not its commit (minutes). Entry tests leakage and provenance are literals True.

## Counterexample (new)

Script: /home/claude/pi_orchestration/skeptic/cm2_counterexample.py. A scratch repository commits a 2-line ledger at T1; the outcome is read at T1+600; a later commit at T1+1200 replaces the ledger with a fresh, valid chain whose two prediction lines carry different numbers, plus an outcome line. Result: `M.verify` ok, `is_append_only(old, new)` False, `commit_times()` still anchors both rewritten lines at T1, and `promotion.admissibility` returns no problem. Nothing in the suite or the daily preflight catches it (the preflight compares the working ledger only with HEAD). The daily script itself never writes such a commit (PI-D-128), so this needs a manual or merged commit; it shows the "checked from git" guarantee is weaker than stated.
